# Задание 1. Исследование моделей и инфраструктуры

## 1. Контекст задачи

QuantumForge Software работает с чувствительной инженерной и регламентной документацией, частью которой нельзя без ограничений передавать во внешние сервисы. Для RAG-бота важны не только качество ответа, но и баланс между безопасностью, стоимостью, скоростью внедрения и масштабируемостью.

## 2. Сравнение LLM-моделей

### Облачные OpenAI / YandexGPT vs локальные Hugging Face

- Качество: облачные модели дают более стабильные ответы на сложные технические и регламентные вопросы.
- Скорость: облачные решения быстрее в эксплуатации и лучше выдерживают пиковые нагрузки.
- Стоимость: локальные модели требуют больших начальных вложений в железо, DevOps и поддержку; облачные — проще в стартовом запуске.
- Развёртывание: облако запускается за часы, локальная инфраструктура — за недели.

Вывод: для MVP и быстрого старта лучше использовать облачную LLM. Локальные модели оправданы только для сценариев с жёсткими требованиями к изоляции данных.

## 3. Сравнение моделей эмбеддингов

### Sentence-Transformers vs OpenAI Embeddings

- Скорость индексации: локальные эмбеддинги быстрее и удобнее для регулярной переиндексации большого объёма документов.
- Качество поиска: OpenAI Embeddings обычно лучше по семантике и многоязычности, но Sentence-Transformers достаточно хороши для корпоративного RAG.
- Стоимость: локальные эмбеддинги дешевле в эксплуатации, облачные — удобнее, но зависят от объёма токенов.

Вывод: для текущего масштаба QuantumForge оптимальны локальные Sentence-Transformers: они дают хороший баланс между качеством, стоимостью и контролем данных.

## 4. Сравнение векторных баз

### FAISS vs ChromaDB

- FAISS: быстрее и проще для MVP, но требует больше ручной работы по persistence, метаданным и поддержке индексов.
- ChromaDB: чуть сложнее в начале, но удобнее для продакшена: есть встроенное хранение, метаданные, удобная работа с обновлениями документов.

Вывод: для продукта, который будет расти и развиваться, лучше ChromaDB.

## 5. Рекомендуемая конфигурация сервера

Ориентир по нагрузке:

- около 18 000 Markdown/MDX, 3 000 страниц Confluence и 250 PDF;
- 200–300 запросов в день;
- 5–10 одновременных пользователей.

Рекомендуемый стартовый сервер:

- 8 vCPU
- 32 GB RAM
- без GPU на первом этапе

GPU потребуется только если позднее появится необходимость в полностью локальной LLM.

## 6. Варианты архитектуры

### Вариант 1. Облачный

- OpenAI / YandexGPT
- OpenAI Embeddings
- FAISS
- Docker + Compose

Плюсы: быстрый запуск, простота, высокое качество. Минусы: данные уходят в облако.

### Вариант 2. Гибридный (рекомендуемый для QuantumForge)

- облачная LLM
- локальные Sentence-Transformers
- ChromaDB

Плюсы: хороший баланс безопасности, стоимости и качества. Минусы: архитектура чуть сложнее.

### Вариант 3. Полностью локальный

- Hugging Face LLM
- Sentence-Transformers
- ChromaDB
- GPU-сервер

Плюсы: максимальная изоляция данных. Минусы: высокая стоимость и сложная поддержка.

### Вариант 4. Продуктовый

- гибридная архитектура
- мультитенантность
- изоляция данных по командам и проектам

## 7. Финальная рекомендация

Для QuantumForge Software на текущем этапе оптимальна гибридная архитектура:

- облачная LLM для качества ответов и скорости работы;
- локальные эмбеддинги Sentence-Transformers для контроля стоимости и снижения риска утечки данных;
- ChromaDB как векторная база для продакшен-работы с метаданными, обновлениями и ростом объёма знаний.

Этот вариант лучше всего соответствует целям компании: он даёт быстрый старт, остаётся экономически разумным и обеспечивает основу для дальнейшего масштабирования.
